# HevaSEO — Backend Migration Plan

Moving HevaSEO from Phase-0 mock data to a live Supabase Postgres backend, one domain at a
time, without ever breaking the frontend. All mock builder signatures stay identical throughout.

---

## 1. Cutover Order (B3 → B9)

Domain order is driven by FK dependencies: you can't query orders without catalog rows, can't
compute payroll without orders, can't derive affiliate commission without both orders and
affiliate rows.

```
B3 Seed
  │
  ├─► B4 Catalog + Customers + Orders
  │     (catalog_services / catalog_packages / catalog_addons →
  │      customers / projects / project_folders →
  │      orders / order_brief_fields / order_addons / order_bundle)
  │
  ├─► B5 Staff Work
  │     (staff / managers / staff_availability / staff_work_hours /
  │      leave_requests / deliverables / assignment_rules)
  │     (depends: orders exist in DB from B4)
  │
  ├─► B6 Finance & Payroll
  │     (pay_overrides / pay_presets / payroll_records / payroll_gig_counts /
  │      staff_penalties / staff_wallet_entries / staff_payout_methods /
  │      staff_payout_requests / transactions / invoices / invoice_orders)
  │     (depends: staff+orders needed to compute payroll; deliverables for gig counts)
  │
  ├─► B7 Affiliate
  │     (affiliates / affiliate_referrals / commission_events /
  │      affiliate_payout_requests / program_rules / affiliate_tier_config /
  │      marketing_assets)
  │     (depends: customers must exist in B4; orders for internal commission_events)
  │
  └─► B8 Messaging & Content
        (broadcasts / broadcast_audiences / broadcast_receipts /
         docs / doc_audiences / doc_resources /
         notes / note_attachments)
        (depends: users/roles from B2; no data dependency on B4–B7,
         but logically last because it's the layer the other domains write into)

  B9 Tickets, Audit, Settings, Analytics
        (tickets / ticket_messages / audit_events / audit_diffs /
         notifications / settings_sla / settings_routing / settings_scoring /
         email_templates / integrations)
        (depends: customers+orders+staff from B4–B5)
```

### Rationale (one line each)

| Phase | Rationale |
|-------|-----------|
| B4 Catalog + Customers + Orders | All other domains reference `orders` and `customers` as FK roots — must land first. Catalog is a prerequisite for placing or reading orders. |
| B5 Staff Work | Tasks, deliverables, availability, and assignment rules all FK to `orders` and `staff`; manager-scope builders join staff → orders. |
| B6 Finance & Payroll | Payroll reads delivered-gig counts from `deliverables` (B5) and uses `orders.value` for commission basis (B4); can't reconcile until both exist. |
| B7 Affiliate | Commission events point at `orders.id` (or an external-order jsonb); referrals point at `customers.id`; tier math depends on real order volume from B4. |
| B8 Messaging & Content | Broadcasts and docs have no upstream FKs from other domains; notes are per `users.id`. Deferred to B8 because these are "localStorage to table" cutovers — no relational dependency on B4–B7 data, but logically follow the core domain. |
| B9 Tickets / Audit / Settings | Tickets FK to `customers`, `orders`, and `staff` (all B4–B5). Audit events are emitted by every earlier domain — the table must exist from B1 but the builder cutover waits until all other writers are live. Settings have no FKs and could land earlier, but they carry no urgency because the mock defaults suffice. |

## 2. Seeding Existing Mock Data

### Strategy

The mock constants in `data/adminMock.ts`, `data/staffMock.ts`, `data/affiliateMock.ts`,
`data/affiliatePortal.ts`, `data/mock.ts`, and `data/services.ts` are the canonical demo
data set. Seeding converts them into SQL so the DB shows the same familiar rows the
frontend already renders.

**Seed script: `supabase/seed.ts`** — a TypeScript file run once with the service-role client
(`SUPABASE_SERVICE_ROLE_KEY`). TypeScript is preferred over raw SQL because:

- The mock constants are TypeScript — the seed can import them directly and iterate over the
  arrays, eliminating transcription errors.
- Date anchoring (see §2.2) is easier to express as code than as SQL expressions.
- Referential integrity order (insert parents before children) can be expressed as `await`
  chains rather than carefully ordered SQL blocks.

The seed is also committed to `supabase/seed.sql` (generated by running the TS script with
`--dry-run` and capturing the emitted SQL) so `supabase db reset` always restores a clean
demo state.

### 2.2 Date anchoring: MOCK_TODAY → CURRENT_DATE-relative

`MOCK_TODAY = '2026-06-24'` (from `lib/today.ts`) is the frozen "now" around which all
order deadlines, created dates, penalty months, and payroll periods are clustered.

When seeding, replace hardcoded ISO literals with offsets from the real clock:

```typescript
// In supabase/seed.ts
const ANCHOR = new Date(MOCK_TODAY); // 2026-06-24
const today = new Date();
const offsetDays = Math.floor((today.getTime() - ANCHOR.getTime()) / 86_400_000);

function shiftDate(iso: string): string {
  const d = new Date(iso);
  d.setUTCDate(d.getUTCDate() + offsetDays);
  return d.toISOString().slice(0, 10);
}

// Usage: order.created → shiftDate(order.created)
// Usage: order.deadline → shiftDate(order.deadline)
// For period_month strings (YYYY-MM), shift the month component similarly.
```

This keeps deadlines, "overdue" indicators, and the payroll period explorer showing recent
data regardless of when B3 runs. The migration doc note in `DATA-ACCESS.md §1.3` applies
identically here: the DB clock becomes the source of truth; `MOCK_TODAY` is retired as soon
as `lib/today.ts` is swapped to `new Date()`.

## 3. localStorage Stores → Tables

There are **9 browser-persisted stores** across 5 files. None have existing server data to
migrate — they are per-browser, per-session state. The cutover is a swap (new code writes
to the DB), not a backfill.

### 3.1 Notes (`data/notesStore.ts`)

**localStorage keys:**
- `heva:admin:notes:v1`
- `heva:manager:notes:v1`
- `heva:staff:notes:v1`
- `heva:customer:notes:v1`

**Target table:** `notes`

**Per-surface keying as columns:**
The four `localStorage` keys map to the `owner_role` column (`admin`, `manager`, `staff`,
`customer`). The `owner_id` column maps to `auth.uid()`. RLS policy:

```sql
CREATE POLICY notes_owner ON notes
  USING (owner_id = auth.uid());
```

This replaces both the key-namespace isolation AND the seed-surface guard in one policy.

**Server Action replacing client write:** `createNote`, `updateNote`, `deleteNote`
(defined in `DATA-ACCESS.md §3.5`). Called from `apps/app/src/server/actions/notes.ts`.

**Staff seed:** `SEED_NOTES` (from `data/staffNotes.ts`) is seeded into the `notes` table
with `owner_id = <staff-s3-user-id>` and `owner_role = 'staff'` during B8. Other surfaces
(`admin`, `manager`, `customer`) start with zero rows — matching the current `seedForSurface()`
logic (`EMPTY_NOTES` for non-staff). No `notFound()` regression: the empty state is the
intentional behavior.

**Correctness fix applied:** The `notesStore`'s SSR default `return SEED_NOTES` (line 27 of
`notesStore.ts`) fires for every surface during server render, causing hydration mismatches.
Once notes are DB-backed, the Server Component fetches the correct surface's rows before
rendering — no `window.location` routing hack needed.

### 3.2 Docs (`data/docsStore.ts`)

**localStorage keys:**
- `heva:docs:v1` (created/overridden docs)
- `heva:docs:hidden:v1` (tombstoned seed ids)

**Target tables:** `docs`, `doc_audiences`, `doc_resources`

**Mapping:**
- Seed docs (`DOCS` from `data/staffDocs.ts`) become rows with `system = true` (locked from
  deletion at the SQL level).
- Admin-created docs land as `system = false` rows.
- The `hidden` tombstone list maps to soft-delete: `docs.active = false` (backed by the
  `deleteDoc` action's `WHERE system = false` guard; seed docs are deactivated via `active`
  column rather than deleted, so they can be restored).
- The `doc_audiences` junction table replaces the `audiences: DocAudience[]` field on
  `StaffDoc`.

**Server Actions replacing client write:** `publishDoc`, `updateDoc`, `deleteDoc`
(in `DATA-ACCESS.md §3.5`).

**RLS:** Audience-scoped read. Staff sees rows where `doc_audiences.audience IN ('general', ...skills)`.
Admin sees all. Enforced by the policy in `RLS.md`; the `docsForStaff()` query in
`server/queries/docs.ts` uses `DISTINCT ON (d.id)` to avoid duplicates when a doc matches
multiple skill audiences.

### 3.3 Broadcasts (`data/broadcastStore.ts`)

**localStorage keys:**
- `heva:broadcasts:v1` (admin-created/overridden broadcasts)
- `heva:broadcasts:hidden:v1` (tombstoned seed ids)
- `heva:broadcasts:activity:v1` (admin activity feed)
- `heva:broadcast:read:<audience>` (per-audience read receipts)
- `heva:broadcast:dismissed:<audience>` (per-audience dismissed banners)
- `heva:broadcast:acked:<audience>` (per-audience acknowledgements)
- `heva:broadcast:clicked:<audience>` (per-audience CTA clicks, from `broadcastStore.ts` +
  `broadcastAnalytics.ts`)

**Target tables:** `broadcasts`, `broadcast_audiences`, `broadcast_receipts`

**Mapping:**
- `heva:broadcasts:v1` + `heva:broadcasts:hidden:v1` → `broadcasts` + `broadcast_audiences`
  (same seed/tombstone pattern as docs).
- `broadcast_receipts` (one row per `broadcast_id × user_id`) replaces the four per-audience
  `read/dismissed/acked/clicked` keys. The `audience` key-suffix is replaced by the
  `users.id` FK — RLS enforces each user only reads their own receipt row.
- The `heva:broadcasts:activity:v1` admin feed → `audit_events` rows with
  `entity = 'broadcast'` (or a small `broadcast_activity` derived view). No separate table
  needed; the admin UI reads from `audit_events` filtered by entity.

**Server Actions replacing client writes:** `sendBroadcast`, `editBroadcast`,
`recallBroadcast`, `markBroadcastRead`, `ackBroadcast`
(in `DATA-ACCESS.md §3.5`).

**`broadcastAnalytics.ts` overlay:** The deterministic RNG + localStorage overlay
(`applyOverlay`) is a Phase-0 demo device. Once `broadcast_receipts` is live, analytics
reads real rows — the overlay is deleted.

**RLS:**
```sql
-- Audience can read their own receipts only:
CREATE POLICY receipts_own ON broadcast_receipts
  USING (user_id = auth.uid());

-- Anyone in the audience can read active, live broadcasts for their role:
CREATE POLICY broadcasts_audience ON broadcasts
  USING (
    active = true
    AND (publish_at IS NULL OR publish_at <= now())
    AND EXISTS (
      SELECT 1 FROM broadcast_audiences ba
      WHERE ba.broadcast_id = broadcasts.id
        AND ba.audience = (auth.jwt() ->> 'role')::broadcast_audience
    )
  );
```

### 3.4 Pay Overrides & Presets (`lib/payOverrides.ts`)

**localStorage keys:**
- `heva.finance.payoutOverrides` (key: `KEY`) — maps `staffId → PayOverride`
- `heva.finance.payPresets` (key: `PRESET_KEY`) — array of `PayPreset`

**Target tables:** `pay_overrides`, `pay_presets`

**Mapping:**
- `heva.finance.payoutOverrides` → `pay_overrides` table (one row per `staff_id`; UPSERT on
  admin save). The `gigRates` and `gigPkgRates` fields stay as `jsonb` columns (documented
  in `SCHEMA.md §11.1`).
- `heva.finance.payPresets` → `pay_presets` table. The ephemeral `id: pp-${Date.now().toString(36)}`
  becomes a proper `uuid DEFAULT gen_random_uuid()` PK.

**Server Actions replacing client writes:** `setPayOverride`, `deletePayOverride`,
`savePayPreset`, `deletePayPreset` (in `DATA-ACCESS.md §3.3`). The `usePayOverride` and
`usePayPresets` hooks become Server Component fetches (`getPayOverride(staffId)`,
`listPayPresets()`).

**RLS:** Admin-only write. Staff can read their own `pay_overrides` row (for the
`effectivePay` display on their finance page) but cannot write it. Manager has no access.

### 3.5 Affiliate Admin Actions (`components/admin/affiliate/shared.tsx`)

**localStorage key prefix:** `heva.affadmin.` (suspend / approve / mark-paid session
state).

**Target:** These are transient in-session admin overrides of mock affiliate status. When the
affiliate domain moves to DB in B7, the actions (`approveAffiliate`, `suspendAffiliate`,
`markAffiliatePayoutPaid`) are Server Actions writing directly to `affiliates.status` and
`affiliate_payout_requests.status`. The `heva.affadmin.*` keys are deleted alongside the
mock. No separate table needed.

### 3.6 UI Preferences (`components/OrdersBoard.tsx`, `components/SettingsView.tsx`)

**localStorage keys:**
- `heva.cardTemplate`, `heva.cardDensity`, `heva.listColumns`, `heva.boardView`
  (OrdersBoard view preferences)
- `heva.set.<id>` (feature toggle states in SettingsView)

**Target:** These are pure UI preferences that belong to the authenticated user. They map to
a `user_preferences jsonb` column on the `users` table (or a separate `user_settings` table
if the settings surface grows). They are **not** part of any B3–B9 domain cutover — they
should be migrated as a small addendum to B9 or as a standalone micro-migration once auth is
wired in B2. No business-logic consequence if left in localStorage temporarily post-B2.

## 5. Dual-Run / Rollback

### How unconverted domains keep using mock while converted ones use DB

The contract established in `PLAN.md §1` makes this trivial: each domain's public builder
functions are the only interface the frontend touches. While a domain is unconverted, its
builder body imports from `data/adminMock.ts` (or the relevant mock file). Once converted,
the body imports from `server/queries/<domain>.ts` instead. Both versions export the same
function name and signature — the call site never changes.

This means at any moment during the migration, a page like `/admin/orders/[id]` can be
reading `buildOrderDetailProps` from the DB while `/admin/finance` is still reading
`buildPayrollPeriods` from the mock. No feature flag, no environment toggle needed — the
per-builder swap is the flag.

### Rollback a single domain

1. Revert `apps/app/src/server/queries/<domain>.ts` to the mock body (git revert the single
   file or restore from the pre-swap commit).
2. Remove or comment out the `server/actions/<domain>.ts` import in the relevant page/layout.
3. Restore the mock import in the builder file.
4. `pnpm --filter @heva/app exec tsc --noEmit` to confirm no type errors.
5. The migration SQL stays in place (non-destructive) — the DB tables remain, the frontend
   just stops reading them.

No other domain is affected by the rollback because each domain's builders are independently
swapped.

### Rollback is safe because

- Migrations are additive (new tables, never DROP or ALTER columns during cutover phases).
- The mock data files are not deleted until `B10 — Hardening` explicitly removes them.
- The seed script is idempotent (`ON CONFLICT DO NOTHING` or `UPSERT`), so re-running
  `supabase db reset` after a rollback restores the expected demo state.

## 6. Data-Correctness Fixes During Migration

The following known mock gaps (flagged in `docs/audit/REPORT.md` as deferred /
backend-era) must be fixed as each domain lands in the DB, not separately. They are not
cherry-picked fixes — they are the natural result of doing the cutover correctly.

### Fix 1 — MOCK_TODAY → real clock (ALL phases)

**Gap:** `lib/today.ts` exports `MOCK_TODAY = '2026-06-24'` as a frozen constant. All date
comparisons (`daysToDue`, `currentPenalties`, `weekDeadlines`, period filtering) are offset
from this anchor.

**Fix during migration:** The `DATA-ACCESS.md §1.3` rule applies to every builder swap:
replace `MOCK_TODAY` / `POD_TODAY` with `CURRENT_DATE` in SQL or
`new Date().toISOString().slice(0, 10)` in TypeScript. Once the last domain is converted,
`lib/today.ts` is simplified to:

```typescript
// lib/today.ts — after backend lands
export const TODAY = new Date().toISOString().slice(0, 10);
```

The `mockTodayDate()` and `mockTodayAt()` exports are removed; their call sites are updated
as each domain is swapped. This is the **highest-priority correctness fix** because frozen
dates cause "overdue" and "due soon" indicators to drift into nonsense once the real clock
diverges from 2026-06-24.

### Fix 2 — Module-scope singletons keyed to demo persona s3 (B5)

**Gap:** `staffMock.ts` exports `CURRENT_STAFF = { id: 's3', name: 'Huy N.', ... }` as a
module-scope constant. `myTasks()`, `MY_TASKS`, and all availability/notification state read
from this constant. When an admin impersonates a different staffer (e.g., `s4 = 'Aria K.'`),
`MY_TASKS` still returns the s3 curated board because the module is evaluated once at import.
The guard on `staffId === CURRENT_STAFF.id` means impersonated staffers partially escape the
singleton but `MY_AVAILABILITY`, `STAFF_NOTIFICATIONS`, and `programStats()` / `joinOffer()`
(affiliate) still read module-scope values frozen to the demo persona.

**Fix during migration (B5 for staff, B7 for affiliate):** Replace module-scope constants
with per-request DB reads:

- `currentStaffId()` → `supabase.auth.getUser()` → look up `staff.user_id` (or read the
  `heva_as` impersonation cookie). No module-scope constant.
- `myTasks(staffId)` → `server/queries/staff.ts` → `SELECT * FROM orders WHERE staff_id = $1`.
- `MY_AVAILABILITY` → `SELECT * FROM staff_availability WHERE staff_id = $1` on each request.
- `STAFF_NOTIFICATIONS` → `SELECT * FROM notifications WHERE user_id = $1 ORDER BY ts DESC`.
- `programStats()` / `joinOffer()` (affiliate) → `SELECT * FROM program_rules` + fresh
  `affiliate_tier_config` rows on each request.

Result: impersonation is correct by construction — every page renders the data for whoever
`supabase.auth.getUser()` (or the impersonation cookie) resolves to.

### Fix 3 — notesStore staff-seed scoping (B8)

**Gap:** `notesStore.ts` line 27: `if (typeof window === 'undefined') return SEED_NOTES` —
the SSR path returns the staff seed for all surfaces. On hydration, `seedForSurface()` runs
and returns the correct surface seed, but there is a mismatch window. Additionally, the
`/manager` surface currently seeds staff-flavoured notes even though a manager is not a
staffer.

**Fix during migration (B8):** The notes table's `owner_role` column and
`owner_id = auth.uid()` RLS policy replace the URL-path routing hack entirely. The
Server Component fetches `SELECT * FROM notes WHERE owner_id = $1 AND owner_role = $2` with
the session's role. No SSR default needed; no hydration mismatch possible. The `SEED_NOTES`
array is inserted into the DB for `owner_role = 'staff'` rows only (§3.1). Manager notes
start empty in the DB, matching the intended behavior.

### Fix 4 — Financial fields in manager hydration payload (B5/B6)

**Gap:** `docs/audit/REPORT.md` deferred item: "Financial fields in manager hydration
payload — never rendered, but strip at the data layer once real auth lands." Currently,
`adminMock.ts`'s `STAFF` array includes `composite`, `quality`, `onTime`, `throughput`, and

policy to `pay_overrides` and `payroll_records` in B6 before the finance builder is swapped.

### Fix 5 — Affiliate frozen stats (B7)

**Gap:** `affiliatePulse.ts` → `programStats()` and `joinOffer()` read from module-scope
constants (`'Paid last month'`, countdown-to-next-payout) authored at build time, so they
are frozen regardless of the current date.

**Fix during migration (B7):** `programStats()` becomes a DB read: month-to-date commission
from `commission_events` filtered to the current calendar month; payout countdown from
`program_rules.hold_days` + the most recent cleared commission's `at` timestamp. The frozen
